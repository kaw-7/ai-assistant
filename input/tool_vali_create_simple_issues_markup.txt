Rules on the top have higher priority (are more important) than rules on the bottom, i.e. if two rules conflict with each other, 
the rule defined earlier in the document override the later defined one.

### MARKUP FIELD DEFINITIONS ###
When creating the structured markup format, use the exact headers:
[[ Description ]], [[ Defect ID ]], [[ Defect Description ]], [[ Source ]], [[ Risk Assessment ]], [[ Status ]] and [[ END ISSUE ITEM ]].
in the given order.
Ensure every issue item follows strictly, the predefined markdown schema without deviation in order or presence of fields.
The value of each field is put on a separate, single line. The issue ends with [[ END ISSUE ITEM ]] and then the next issue
must start with [[ Description ]]. Do not plug empty lines in between [[ END ISSUE ITEM ]] and [[ Description ]].
Do not plug empty lines in between fields - only when the field is empty.

Description is a short description of the issue/bug. 
If the bug is about improvements, updates, upgrades, licesning, system requirements, documentation and similar notes 
then put: "MARKER! This is an improvement/update/upgrade/etc". If you cannot find any short description 
in the free text document and if the issue does not fall in the cathegory defined in the previous sentence, 
then you need to provide a short heading for that issue/bug. 
Defect ID is the issue/bug ID. If not present in the free text document, create a default one. 
Defect Description is the actual defect description - it is usually a long description of the issue with some details, examples, etc. Do not modify this, take the specification from the free text document as it is!
Source field has to be mapped to one of these specific values: KNOWN_PROBLEM_BY_VENDOR, KNOWN_PROBLEM_3RD_PARTY, CORRECTION_IN_REL_NOTES, KNOWN_PROBLEM_IN_NEWER_VERS, OCCURED_AT_OTTOBOCK, or OTHER_SOURCE.
Risk Assessment is empty for all items.
Status is set to default NOT_EVALUATED for all items.

KNOWN_PROBLEM_BY_VENDOR - known issue published by vendor
KNOWN_PROBLEM_3RD_PARTY - known issue published by 3rd party source
CORRECTION_IN_REL_NOTES - correction of issue fixed by vendor
KNOWN_PROBLEM_IN_NEWER_VERS - known issue which occured in a newer/later version of the software tool
